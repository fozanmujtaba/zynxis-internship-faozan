# Week 7 — Autonomous Business Logic

**Task:** Build a "Startup Operations Agent" for Zynxis that takes raw client
requirements and generates a Task Breakdown, Timeline, and Tech Stack
recommendation.

## What This Demonstrates

| Concept | How it's shown |
|---|---|
| Staged reasoning | Three LLM calls, each consuming the last: analyse the brief → break down the work → recommend a stack. Each asks for a different kind of judgement |
| Structured output | Every stage returns JSON via Groq's `response_format=json_object`, so parsing never depends on the model not wrapping its answer in a code fence |
| Deterministic business logic | Dates, the critical path, and resource contention are computed in `schedule.py` — not generated by the model |
| Validation before trust | `validate_breakdown()` checks the task graph (unique ids, resolvable dependencies, sane estimates) and **reports every repair in the output** |
| Surfacing ambiguity | The agent is instructed to name what the brief left unsaid, and to state the assumption it planned against, so the cost of a wrong assumption is visible |

## Pipeline

```
brief.md
   │
   ├─► [1] analyse      (LLM)  → scope, open questions, risks, complexity
   │
   ├─► [2] break_down   (LLM)  → epics + tasks with estimates & dependencies
   │        │
   │        └─► validate (code) → repair duplicate ids, bad estimates,
   │                              unresolvable dependencies
   │
   ├─► [3] schedule     (code) → topological sort, per-role capacity,
   │                              working-day calendar, critical chain
   │
   └─► [4] tech_stack   (LLM)  → 8 layers, each with a rejected alternative
                                  │
                                  ▼
                    task_plan.md → task_plan.pdf + plan.json
```

## Why the model doesn't get to pick the dates

Ask an LLM to add nine working days to a Thursday while respecting two
upstream dependencies and a shared engineer, and you will get a confident,
plausible, wrong answer — and no way to tell it is wrong by reading it.

So the division of labour is explicit. The model contributes domain judgement:
what work exists, roughly how big each piece is, what depends on what. The
code contributes arithmetic that is correct by construction: topological
ordering, weekend-aware date maths, per-role capacity, and the critical chain.

**On the critical path specifically.** Textbook CPM walks the dependency graph
alone. On a capacity-constrained plan that reports slack which does not exist:
if one engineer must finish A before starting B, then A slipping delays B
whether or not the graph says so. `build_schedule()` records those queueing
edges as `resource_pred`, and `mark_critical_path()` includes them — so what
comes out is the critical *chain*, consistent with the schedule actually
produced.

The difference is easy to see. Three tasks, T1(2d) → T2(3d) plus an
independent T3(2d), all Backend Engineer:

| Team | T3 slack | Critical tasks |
|---|---|---|
| 2 backend engineers | 3 days | T1, T2 — T3 floats |
| 1 backend engineer | 0 days | all three — the engineer serialises them |

Same task graph, different answer, because the constraint is people rather
than dependencies.

## Results

Run against [briefs/fintech_app.md](briefs/fintech_app.md) — a deliberately
messy, realistic enquiry from a Kenyan fintech founder, written the way clients
actually write, with the AI feature hedged as "might be phase two" and the
regulatory position admitted as unknown.

**Output:** 7 epics · 30 tasks · 84 person-days · 67 working days
(~13.4 weeks) across an 8-person team · 26 tasks on the critical chain.

The plan fits inside the client's stated four-month runway, which is the
question they actually asked.

The agent's strongest output is the **Open Questions** table. From that brief
it independently flagged the CBK regulatory position, the undefined dispute
resolution process, and the unclear training data for the default-prediction
model — each paired with the assumption the schedule currently runs on.

## Honest limitations

- **Estimates are the model's opinion.** The scheduling maths on top of them
  is exact, which risks making a guess look like a measurement. The plan is a
  starting point for negotiation with a delivery team, not a commitment.
- **No cost model.** Person-days are computed but never priced; day rates vary
  too much by market for a default to be meaningful.
- **The calendar knows about weekends and nothing else.** Public holidays,
  leave, and part-time allocation are not modelled, so long plans drift
  optimistic.
- **One task, one role.** Real tasks often need a designer and an engineer
  together; here each task consumes exactly one person from one role.
